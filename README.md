## Setup and usage

Run these commands from the repository root.

Install all project dependencies:

```bash
make setup
```

Run the complete data pipeline. This creates or refreshes `databaseSchema.db`
and regenerates all tables, plots, statistical results, and query outputs:

```bash
make pipeline
```

Start the interactive Streamlit dashboard after the pipeline finishes:

```bash
make dashboard
```

The dashboard is served locally by `dashboard.py`.

To run only the database-loading step independently, use:

```bash
python load_data.py
```

This creates or refreshes `databaseSchema.db` in the repository root and does
not run the Part 2, Part 3, or Part 4 scripts. On a new machine, run
`make setup` first because `load_data.py` requires the `pandas` dependency from
`requirements.txt`. After dependencies are installed, `load_data.py` can be
run independently without running the rest of the Makefile pipeline.

## ERD / Schema Diagram. How it scales and supports analytics 

The current Schema Diagram has taken the original `cell-count.csv` and converted it into 4 different entity relations. 
1. `Subject`: Contains:
- `subject` P.K. from `cell-count.csv.subject`
- `condition` from `cell-count.csv.condition`
- `age` from `cell-count.csv.age`
- `sex` from `cell-count.csv.sex`
- `project` from `cell-count.csv.project`

2. `Treatment`: Contains:
- `treatment_id` P.K. generated by SQLite with autoincrement
- `subject` F.K. to `Subject.subject`, from `cell-count.csv.subject`
- `treatment` from `cell-count.csv.treatment`
- `response` from `cell-count.csv.response`

3. `Sample`: Contains:
- `sample` P.K. from `cell-count.csv.sample`
- `subject` F.K. to `Subject.subject`, from `cell-count.csv.subject`
- `sample_type` from `cell-count.csv.sample_type`
- `time_from_treatment_start` from `cell-count.csv.time_from_treatment_start`

4. `CellFrequency`: Contains:
- `sample` composite P.K. and F.K. to `Sample.sample`, from `cell-count.csv.sample`
- `population` composite P.K., one of the five immune-cell populations
- `percentage` calculated as `count / total_count * 100`
- `count` from the matching population column in `cell-count.csv`
- `total_count` calculated by summing the five population counts for each sample

# Relationships :

`Subject` and `Treatment` have a 1:1 relationship where one Subject has *one* Treatment record. 
`Subject` and `Sample` have a 1:N relationship where one Subject has N (3) Sample records. 
`Subject` connects to `CellFrequency` through `Sample`, where one Subject has N (15) CellFrequency records 
`Sample` and `CellFrequency` have a 1:N relationship where one Sample has N (5) CellFrequency records

# Why this scales well : 

This Schema Diagram works well because it preserves data without repition, ensuring that all non-key fields 
strictly relate to the key fields to not only maintain normalization, but also reduce repeated data and rows for a specific Subject
or Sample. The `Subject`, `Treatment`, `Sample`, and `CellFrequency` tables are connected through primary and foreign keys. 
This avoids repeatedly storing patient and treatment metadata for every cell population measurement.

The diagram scales well as future projects will allow all these relations to be in their own normalized, independent tables. 
For example, cell populations are now converted into a singular column based on their value counts, rather than needing 5 respective columns. 
Subject data will not need to be repeated 5 times for cell frequencies on each sample of 3 (causing 15 records). New projects past `prj3` can be allowed without needing to add new columns or changing the database structure. 

This structure is great for analytics as data analysts will be able to filter and aggregate data by `project`, `condition`, `treatment`, 
`response`, `sex`, `sample_type`, etc. using SQL `JOIN`s rather than manipulating `.csv` files through Python string manipulation or 
`pandas` DataFrame wrangling. As seen in my EDA notebook or the `load_data.py` or `part4_queries.py`, an analyst will be able to `INNER JOIN` 
all 4 tables together seamlessly to get a specific population or sample group. 

# Overview of Code :

`load_data.py` reads `cell-count.csv`, creates the SQLite database, defines the relational schema, and loads the source data into the `Subject`, `Treatment`, `Sample`, and `CellFrequency` tables. The assessment asked for cell frequencies, but I found it best to store the frequencies as 'CellFrequency'
as persistent data so that any future python files may easily query from that table rather than manipualting or storing the table again. This also
gave me clarity in how I wanted to go back and restructure my original schema diagram, which orignally contained 3 tables, but turned into 4 with much easier
normalization with the introduction of CellFrequency. 

`part2_analysis.py` queries the normalized `CellFrequency` table and exports the Part 2 relative-frequency summary to
`outputAnswers/part2_CellFrequency.csv`. Each source sample produces one row for each of the five immune-cell populations.

`part3_stats.py` filters the data to melanoma patients receiving miraclib with PBMC samples. It creates responder versus non-responder boxplots, runs the logistic regression analysis, calculates cross-validated performance metrics, and performs Mann-Whitney U hypothesis tests.


`part4_queries.py` contains the required SQL queries for baseline melanoma PBMC samples and the B-cell analysis for male melanoma responders. Each result is exported to the outputAnswers directory.


## How the assessment runs

The Makefile follows the assessment's required order. `make setup` installs every
third-party dependency listed in `requirements.txt`. `make pipeline` then runs
the complete workflow without manual intervention:

1. `load_data.py` reads `cell-count.csv`, recreates `databaseSchema.db`, and loads the four normalized tables.
2. `part2_analysis.py` writes the cell-frequency summary for Part 2.
3. `part3_stats.py` generates the responder/non-responder boxplots, statistical evidence, logistic-regression coefficients, and model metrics.
4. `part4_queries.py` runs the required SQL subset queries and writes their CSV outputs.

Finally, `make dashboard` starts the Streamlit dashboard in `dashboard.py`.
The dashboard presents the findings first, followed by the Part 4 query answer,
the database table explorer, and the PlantUML schema diagram.
